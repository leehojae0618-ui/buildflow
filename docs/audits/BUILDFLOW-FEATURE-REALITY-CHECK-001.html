실행 가능 vs 실행 불가능 — 코드 기준 기능 실태 보고서

2026-07-31 대상: leehojae0618-ui/buildflow @ main 방법: 3개 영역 코드 직접 추적 (문서 상태 아님)
한 줄 결론. BuildFlow는 지금 "AI Agent Factory"가 아니라, 잘 만들어진 프로젝트·워크플로 트래커 + 큐레이션 추천 라이브러리다. AI 에이전트를 실제로 빌드하고 실행하는 핵심 파이프라인(Core Runtime)은 OpenAI와 실제로 통신할 수 있는 코드로 존재하지만, 화면 어디에도 이를 호출하는 버튼이나 라우트가 없다—즉 사용자는 오늘 이 제품으로 AI 에이전트를 한 번도 실행시킬 수 없다.

A. 실행 가능한 기능

실제 로그인 사용자가 배포된 화면에서 지금 바로 쓸 수 있고, 데이터가 Supabase에 실제로 읽고 쓰이는 기능.

기능상태실사용 도움 수준근거
회원가입 / 로그인 (이메일, Google) 완전 동작 상 — 모든 기능의 전제조건 features/auth/actions.ts
app/auth/callback/route.ts
프로젝트 생성 / 수정 / 보관 완전 동작 상 — 실 DB write, UUID 검증 features/projects/actions.ts
Workflow Step 진행률 저장 완전 동작 상 — 새로고침·재로그인에도 유지 features/workflows/actions.ts
Dashboard 요약 / 최근 활동 완전 동작 중 — 실 집계, 빈 상태 처리 포함 features/dashboard/queries.ts
Tool Explorer / Workflow Library 완전 동작 중 — 큐레이션 콘텐츠 품질에 좌우 features/discovery/queries.ts

“AI”라는 이름이 붙었지만 실제로는 규칙 기반

goal-parser.ts는 목표 문장을 한국어 키워드 매칭 규칙표로 분류한다 — LLM 호출이 없다. constraints.ts의 Capability Calculator도 동일하게 하드코딩된 조건식이다. 실제 OpenAI 연동은 별도 기능인 Recommendations(features/recommendations/enrich.ts)에 있는데, 여기 기본 모델 값이 존재하지 않는 문자열("gpt-5.6-luna")로 박혀 있어 검증되지 않은 placeholder 설정으로 보인다. 사용자에게 "AI가 분석해준다"고 기대하게 만드는 지점과 실제 구현 사이에 간극이 있다.

B. 실행 불가능한 기능

코드 자체는 실재하고 종종 테스트까지 통과하지만, 화면·API 어디에서도 사용자가 도달할 방법이 없는 기능.

기능상태왜 못 쓰는지근거
Core Runtime (AI 에이전트 실행 엔진) 연결 없음 실제 OpenAI 어댑터로 동작 가능(스모크 테스트로 검증됨)하지만 .tsx 어디서도 호출되지 않음. 버튼·라우트 부재. features/agents/runtime-orchestrator.ts
Runtime Evidence 저장소 연결 없음 Supabase 어댑터·checksum 로직 실재. 테스트는 mocked client만 사용, DB 레벨 미검증. features/agents/runtime-evidence-supabase.ts
Human Approval (실행 승인) 연결 없음 single-use consume RPC까지 구현됐지만 승인 요청을 보여줄 UI 자체가 없음. features/runtime-approval/runtime-approval-supabase.ts
Product Runtime Bridge 연결 없음 Approval + Evidence + Core Runtime을 엮는 서버 함수. 유일한 호출자가 자신의 테스트 파일. features/product-runtime/execute-approved-product-runtime.ts
MCP (외부 도구 연동) 계약만 존재 권한·위험도 타입과 검증기만 있음. 실제 서버 연결, tool invocation, 재시도, 스트리밍 없음. features/mcp/validator.ts
프로젝트 상세의 “실행” 버튼 오인 주의 Core Runtime과 무관한 별개 기능—단순 DB 태스크 행 생성일 뿐, 실제 AI 실행이 아님. features/execution/actions.ts

오늘 실제로 쓸 수 있는 것

  • 목표를 등록하고 구조화된 요구사항으로 정리하기
  • 큐레이션된 Tool/Workflow를 탐색하고 프로젝트에 선택하기
  • 선택한 Workflow를 단계별로 따라가며 진행률을 저장·복귀하기
  • 여러 프로젝트를 대시보드에서 한눈에 트래킹하기

아직 안 되는 것

  • AI가 목표를 이해해 자동으로 Agent를 설계·빌드해주는 것
  • 만들어진 Agent가 실제로 외부 도구(MCP)를 호출해 작업을 대신하는 것
  • 실행 전 사람이 승인/거부하는 Human Approval 플로우
  • 실행 결과를 신뢰 가능한 Evidence로 남기고 공유하는 것

병목과 우선순위

지금 시점에서 “AI Agent Factory” 정체성을 실현하는 데 가장 큰 병목

  1. 코드가 없어서가 아니라 연결이 없어서 못 쓴다. Core Runtime, Evidence, Approval은 이미 구현·테스트되어 있다. 남은 일은 프로덕트 UI/API 라우트를 붙이는 것이다.
  2. 연결보다 먼저(또는 동시에) 안전장치가 필요하다. MCP 관련 High 기술부채 11건이 열려 있는 채로 실행 경로를 먼저 연결하면, 검증 안 된 도구 호출을 실사용자에게 그대로 노출하는 위험이 생긴다.
  3. CI 자동화 부재는 별도 리스크다. 763개 테스트와 정교한 RLS는 고무적이지만 push/PR에 자동으로 걸리지 않는 한, 다음 변경이 조용히 회귀를 만들 수 있다.

조사 방법: 프로젝트 운영 문서(AGENTS.md, .buildflow/STATUS.md, docs/PROJECT_STATE.md)가 아니라 소스 코드를 직접 추적해 작성함 — grep/read 기반, 3개 영역(제품 UI/라우트, Runtime/Agent/MCP 백엔드, 테스트/CI/기술부채) 병렬 조사.
